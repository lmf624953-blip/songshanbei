# 阶段拆分与 Q 供数：本轮未选用

2026-11-28，在 `f13r1n16` 复核按计算/访存特点拆分 kernel 的建议，并完成三个 Q 分段供数对照。**分数物化拆分已有负收益证据，本轮未重复运行；新增 Q 重载也明显退化。正式配置继续保持已验收的行分片归一化版本，公开 A 稳态完整请求均值 116.975680189 秒。** 本轮没有重新生成完整视频，也没有新的端到端成绩。

## 选择拆分边界

完整 Transformer 原本由多个 kernel 组成；这里同时承担 QK、在线 softmax、PV 的是长注意力融合 kernel。拆分是否有效取决于资源释放和数据传递的实际代价，不能以源文件或 kernel 的规模直接判断。

| 方案 | 数据交换与数值约束 | 实测或当前取舍 |
| --- | --- | --- |
| QK producer→FP32 分数→softmax/PV consumer | 保留原 dot、scale、在线归约和 BF16 RNE 顺序；每个 KV 块分数写回并重新读取 | 此前已实现 AoS/SoA4，生产长度明显退化；复用证据，不重跑 |
| 直接拆出完整 softmax/PV | 仍需要存储完整分数或概率矩阵，必须核算读写量及归约顺序 | 本轮不盲目扩展同类分数物化方案 |
| 并行 split-KV 后合并输出 | 常规方案会改变在线 max、分母及 PV 的累加/舍入路径 | 需要单独证明逐位一致；当前不直接替换 |
| 融合内按阶段缩短 Q 生存期 | Q 每段重载，省出寄存器给其他阶段，避免分数矩阵写回 | 本轮已测；数值通过、耗时约翻倍，不采用 |
| 融合内调整寄存器复用和流水线 | 保留片上交换，避免额外全局中间结果；资源必须跨过实际档位 | 继续作为后续方向；不预报收益 |

此前真正的两 kernel 拆分，将 QK producer 压缩到 120 VGPR，但 27570 / 22016 tokens 从约 19.20 / 13.06 ms 退化到 44.30 / 29.10 ms。27570 tokens 单次增加约 **42.66 GB** 分数读写。全部输出位模式及原始 PMC/trace 见 [历史拆分记录](qk-split-f13r1n16.json)。这只否定已经测过的拆分实现，不能推导所有拆分方案都无效。

## 本轮三个对照

冻结 packed 镜像 SHA-256 为 `a00cc85245e936216531503c3c1dfb57293d00d907dd517b4b1b6c8932f8a3cd`，与当前正式发布相同。仅替换 packed ISA，正式主机库、V 预排布镜像及回退镜像全部逐字节保持。

原 Q 常驻 `v65:96`，占 32 个 VGPR；输出累加器为 `v1:64`。本候选把 Q 改为每次装入 8 个 VGPR，正常块及尾块均保持原来每个 dot 的 MMAC 顺序，再复用腾出的寄存器承载高编号临时值。增加两个持久 Q 地址和相应 mask，保持尾块无效 lane 清零及最终输出 guard。

每个候选先完成 12 个长度的普通/放大 QK/guard 校验，三个候选共 36 项均通过。随后每个生产长度执行 39 对无 profiler 交替事件计时，包含每次 V 预排布和完整注意力。表内为双方样本中位数；百分比是逐对收益中位数，负值表示变慢。

| 模式 | VGPR 描述值 | 27570 tokens：对照→候选 | 逐对收益 | 22016 tokens：对照→候选 | 逐对收益 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 只扩资源配额 | 221 | 19.192951→19.187511 ms | +0.0242% | 13.071835→13.070555 ms | −0.0061% |
| 重载、保留高编号 | 221 | 19.197592→40.852623 ms | −112.8027% | 13.069915→25.873270 ms | −97.9605% |
| 重载、压缩编号 | 198 | 19.197752→41.017578 ms | −113.6832% | 13.070714→25.842880 ms | −97.6155% |

只增加配额基本不改变速度，新增重载则已造成约两倍退化。压缩编号并未挽回该损失。全部正式样本及逐位结果见 [原始汇总](attention-query-reload-f13r1n16.json)。

## 资源门槛与独立 PMC

实际候选调用 `hipModuleOccupancyMaxActiveBlocksPerMultiprocessor` 均报告 **3 blocks/CU**。额外构造了独立符号、仅包含 `s_endpgm` 的描述探针，对 12 档 VGPR、2 档 SGPR、3 档动态 LDS 共 72 项查询资源上限，**没有发射探针 kernel**。该结果不是实际动态 occupancy，也不代表提速：

- 256 线程、16 KiB LDS：本轮 192 及以下 VGPR 档可报告 4 blocks/CU；196、198、219、221 等档仍为 3。
- 24/32 KiB LDS：本轮全部查询档位均报告 2 blocks/CU。因此新增第三块 K 缓冲的 24 KiB 跨块流水线存在降低驻留上限的代价，必须计入设计预算。
- 两档 SGPR（描述值 54/66，元数据含特殊寄存器为 58/70）在本轮查询下没有改变上述门槛。

独立默认 `hipprof --pmc` 的原生 TXT 各包含 2 次注意力调用。下面直接使用 TXT 字段；profiler 内时间不代替前述正式配对成绩。

原始文件：[对照 PMC](attention-query-reload-f13r1n16-reference-pmc.txt)、[重载 PMC](attention-query-reload-f13r1n16-reload-pmc.txt)。bank conflict 的百分比下降时，`shared memory operation` 仍相同，kernel 反而变慢；不能把百分比下降当作冲突绝对代价已经解决。本轮也没有原生 L1 命中率字段，不将 `L1 cache unit is active` 误称为命中率。

另做三个最小汇编能力探针：现用 VGPR MMAC 能构建，AGPR 读写指令被 gfx936 汇编器拒绝，AGPR MMAC 操作数也被拒绝。因此当前目标不采用 AGPR 存储候选；这不是 GPU 性能实测结论。

## 复现、失败保留和后续

源码及命令见 [候选 README](../candidates/attention-query-reload/README.md)。完整实验目录为 `/public/home/acvduipmem/xsh/songshanbei/optimization/dcu-kernel-autotune/validation/attention-register-pipeline-f13r1n16-1795816098852363496`。`summarize.py` 只读取已完成结果，不重新发射任务。

第一次 CPU 静态检查把标签 `.LBB0_2` 与 `.LBB0_20` 作子串匹配而失败，修复后构建通过，未发生 GPU 数值失败。首次 `--pmc-type 3` 成功输出对照原始 CSV，但外层脚本误检查 TXT 而退出 1；CSV 保留。随后使用默认 `--pmc` 补齐双方另一类指标的 TXT，退出 0。所有任务已终态，记录不将上述包装失败改写成成功。

`screen.py` 在正式任务终态后仅为 occupancy 函数新增可选符号和 LDS 参数，默认实际候选查询路径未变；汇总明确归档当前源哈希，不把它冒充启动时冻结快照。构建脚本在最终 CPU 构建后未改变。

当前注意力成本约占完整请求四成，约需可靠 8% 注意力收益，才有接近 3% 完整请求收益的预算。本轮两个负候选不进入八卡整模型、普通入口及成片资格；正式 116.975680189 秒结果沿用已有完整资格，并没有用微测推导一个新的整模型成绩。

下一步先研究**不增加全局中间结果的寄存器生存期/阶段复用**，只有能把实际资源压到有意义的档位，才实测供数重排。跨 KV 块 QK/PV 流水线先核算 LDS 与驻留代价，再决定原型范围；此前裸 MMAC 多累加链没有显著收益，不能仅凭“更多独立链”预测真实提速。若某条方向只有低于 3% 完整请求的可靠单项收益，按既定规则归档；持续目标保持 active，不宣称 kernel 已无优化空间。
